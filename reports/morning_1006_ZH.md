K=50、100：种子已收齐（每个种子集 100 条可信轨迹），Seed-SFT 有 2 个训练任务正在 hpg 上跑，baseline 在排队。

要点：
- **Seed-SFT 随 K 单调上升**，但种子集之间的差异很大，K≤5 时尤其明显。
- **官方配方的 baseline 基本都停在 base 附近**：LEAP 两个版本、AgentGym BC 都是 58–60，AgentEvol 是 66。Kang 是例外，比 base 高，但种子集之间波动非常大（K=20 时 63 到 110 都有）。
- **LEAP 在 K=20 时每轮只拿到 4–8 条教师纠错**：学生在 20 个种子任务上每轮仍有 11–15 局失败，但其中一部分拿不到特权状态（4 个任务没有手写 expert），另一部分纠错格式不合格被拒；官方的"取最小集合"聚合又把训练集压到 160 条。机制上，它学不到什么新东西。

## 2. 环境特质：增益来自"base 不会、且种子里有可迁移示范"的任务类型（表见附件 coverage_by_type.md）

- 加热（base 1/16）、冷却（base 1/25）是 base 几乎完全不会的类型，几乎所有增益都来自这两类；简单类 base 已经 31/35。
- K=5 时每个种子集刚好缺一类：s1 缺的是简单类，所以两种方法都约 100；s0 缺冷却，冷却就停在 base 水平。
- K=1→2 的 s1 最直观：一条"清洗"轨迹学完不超过 60，加一条"冷却"轨迹就到 85–87。
- 只覆盖到还不够：s0 唯一的加热种子迁移不出去（2–3/16），s1 的可以（8–9/16）。

## 3. K=5 学生（s0，40 万 token，rai 上 74/140）的失败机制

gap 集为"教师成功、学生失败"的 43 局，其中 13 局是冷却类。K5 s0 的种子里没有冷却轨迹，这 13 局单独统计，不进入下面的机制拆分。
在剩下 30 局"离成功最近的状态" t\* 上单点干预（救回 = 贪心成功，且 4 次采样中至少 3 次成功；均为相对 I0 的配对超出）：

| 干预 | 本次 K=5 学生 | 之前的 K=20 学生（run2） |
|---|---|---|
| I0 不改动 | 0/30 | 0/24 |
| I1 复述已知事实 | 4 | 3 |
| I2 合法地重新观察 | 4 | 2 |
| I3 教师建议（不给动作） | 8 | 11 |
| **I4 教师直接给动作** | **13** | 9 |
| I5 上下文里放一条同类种子 | 5 | 8 |

按预注册判定表：两种机制都有 4 局，机制 2（需要更明确的决策信息）4 局，机制 1（经验没用上，覆盖检查待做）3 局，只有 I4 能救或都救不回 19/43。
解读：K=5 学生的瓶颈更多在"会不会做这一步动作"（I4 远强于 I3），而 K=20 学生更多是"给一句提示就会"。经验越少，越缺可执行的动作知识，而不只是决策信息。
**加上覆盖检查和知识探针（修订 5）之后的归因**（全部 43 局）：
| 归因 | 局数 |
|---|---|
| 种子里根本没有该类型（冷却） | 13 |
| 所需步骤在种子里没有示范（2 局只有经验类干预能救；4 局只有决策信息类干预能救） | 2 + 4 |
| M1b 学进去了但没用上 | 1 |
| **M1a 没学进去** | **0** |
| M2 需要更明确的决策信息 | 4 |
| 只有教师给动作才能救（执行或能力问题） | 4 |
| 都救不回 | 15 |

训练集拟合 97.5%（K=20 学生是 93.7%），M1a 两次都是 0。
**结论：经验"学不进去"几乎不发生。K 小的时候，主要缺口是经验里本来就没有这类知识（19/43），其次是决策信息和执行能力。** 这和第 2 节的分类型结果对得上。

## 4. 方法学与工程（会进附录）

- **LEAP 移植**：一共修了 5 个工程问题。(1) 官方 prompt 模板没被打包进 git archive；(2) 我们的合并一致性检查比官方严，现改为与官方一致，误差照样记录并披露；(3) 合并后的 checkpoint 缺 processor_config.json；(4) gpt-6-luna 不接受 temperature/top_p，返回的 400 错误 code 为 null，官方采样回退没触发；(5) 第 1 轮起用错了校验器。之后在 CPU 上用一个小号 Gemma-4 把整条链真实跑了一遍，第 5 次提交才跑通全部 4 轮。
- **机制分析修订 6**（在看到任何干预结果之前提交）：FCE 用满单局 700 次教师调用上限的局，允许以 2 倍上限重试一次，教师缓存只读复用。重试后另外 41 局的 FCE 结果与第一次逐项完全相同（已核对）。
- **我犯的两个错**：(a) 把 K=1/2 的子集视图写进了 K=20 种子目录，导致 K=100 的身份校验在 hpg 上失败，K=50/100 因此推迟了约 2 小时（已恢复，内容核对一致）；(b) 一次同步脚本没检查路径，远端 find 返回空，把 hpg 根目录的一部分（74 MB 公共软件和一些空目录）拷到了 rai 项目里。没有任何敏感文件，已移到 _trash。两条都已写进经验记录。
- baseline 原有的 K∈{5,10,20} 校验已放宽到整个阶梯，并逐个方法审计了 K 相关的前提条件（reports/baseline_k_ladder_audit.md）。

## 6. 需要你拍板

1. **LEAP 在 K=100**：第 3 轮可能需要 220–239 次更新，超过我们移植时"<200 次更新、不做留出集、不按步保存"的前提（官方 recipe 在第 200 步做 eval/save，并留出 15% 轨迹）。三个选项：(a) 保留限制，K=100 只报告到能跑的轮次；(b) 把"全部数据 + 最终 epoch"的偏离扩展到 200 步以上，并披露；(c) 在 K=100 恢复官方的留出集和按步选择。我倾向 (b)：与 K≤50 的做法一致，只是需要额外披露。
2. **hpg 资源紧张，要不要收缩 AgentGym 的格子**：比如 K∉{5,10,20} 只跑 s0，周四前更可能出齐。
3. **Kang K=20 s0 要不要换训练 seed 重跑**（昨天问过）：用来区分是配方本身不稳定，还是种子内容的问题。
4. **剂量对照方案**（docs/BASELINE_DOSE_CONTROLS.md）是否开跑：从剂量充足的 Seed-SFT 出发，再叠加各 baseline 的组件。
