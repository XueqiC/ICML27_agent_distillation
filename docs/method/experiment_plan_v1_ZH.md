# 方法完善实验方案 v1：从"可行教学"到"无提示学会"

日期：2026-10-27（CDT）。对应方法设计：[agent_distillation_method_design.md](agent_distillation_method_design.md) 的 §2（方法）与 §3（验证）。本文是执行方案；每个阶段在运行前另写预注册，固定案例、指标和判定规则后才调用 teacher 或训练。

## 0. 目标与原则

- **最终指标**：学生在新任务上、没有任何 teacher 指导时的成功率（设计 §2.1 的 $`J(\theta)`$）。中间实验都服务于这个指标，不以"指导下做对"作为终点。
- **验证顺序**按设计 §3.1 的四层，每层有通过条件，不通过就先修这一层，不跳到下一层：
  1. **V1a 可行教学**：teacher 从学生到达的状态出发，能否完成？
  2. **V1b 指导落实**：持续联合指导能否通过学生自己的执行推进任务？
  3. **V2 独立学习**：把有效交互变成训练数据后，学生脱离提示能否保留？
  4. **V3 条件迁移**：学到的是条件，还是某条路线？
- **复用**已有基础设施：
  - reset 与前缀重放、逐步核对（repair-v01-eval）；
  - CG probe 的注入、rollout 与汇总代码（9f16962）；
  - θ₀ 的继续训练接口（repair-v01-train）；
  - 主网格的评测协议。
- **数据隔离**：
  - U_mech、CG 案例、新的诊断池 U_dev（见 §1.2）只用于诊断和方法开发，永不进入训练。
  - D_probe 的 60 个任务（含 24 个 quick）只用于无指导验证。
  - dev140 只在最后与 baseline 对比时使用，并明确称为 development 集。
- **单 seed 探索**：方法未定型之前，每个训练组只跑一个训练 seed。有正向信号后，先换一个 seed 复核，再扩大规模。

## 1. 阶段 0：工程（Codex 实现，我审核；只新增文件）

| 编号 | 组件 | 内容 | 验收 |
|---|---|---|---|
| E0.1 | Teacher 接管策略 | 用主网格收集示范时的同一 ReAct prompt 和 gpt-6-luna 传输层，作为 `execute_actions` 的 continuation：从重放后的前缀开始逐步行动，每步读取真实 observation | 假环境测试；再在 1 个案例上做 1 次真实 canary |
| E0.2 | Harness 事实表 | 只从公开 observation 推出：持有物（合法 take/move 的结果）、已观察到的物体位置（"you see …" 列表）、容器是否打开过、哪些位置已有充分观察、被拒绝的动作（动作 + 步号）；从任务文本解析目标物体、所需状态、目标位置和数量。每条事实带证据步号；证据不足时记为"未知"。访问过但没打开的容器，不记为"已排除" | 在已有的 4,620 个主网格 episode 上抽查，与人工阅读一致；用单元测试覆盖持有、拒绝、关闭容器等情形 |
| E0.3 | 联合指导循环 G | 每个决策点执行下列步骤，见 §3.1 | 假 teacher + 假环境测试；指导文本与环境原文分开记录；最终评测路径不含任何 Guidance |
| E0.4 | 监督构造器 | 从 G 日志生成 `(x, h_t) → (r̂_t, â_t)` 记录，按设计 §2.4.1 的 7 条规则执行 | 每条记录可以追溯到原始日志；删除 teacher 消息后，前缀是自足的 |
| E0.5 | 训练组 | 复用 θ₀ 继续训练接口：相同优化器、LoRA、loss 归一化；新记录与 K 条原示范混合；保存第 1、5、20 次 update 的 checkpoint，然后继续训练，checkpoint 按固定的 probe 规则选择 | 假模型 dry-run 生成相同的 batch 顺序；在真实模型上跑 1 次 update 的 canary |
| E0.6 | 无提示检验 | 三种：(a) 原困难历史续跑（CG 的 A 分支方式）；(b) 同任务从起点执行；(c) 新任务（D_probe 60 / quick 24） | 与主网格评测协议逐项一致 |

E0.1 和 E0.2 不依赖本方案中尚未确认的决定，可以先做。

### 1.1 Teacher 的三种角色及其提示

| 角色 | 输入 | 输出 |
|---|---|---|
| T：接管 | 与学生相同的 ReAct prompt 和公开历史 | 下一步 Thought/Action |
| R：审阅 | 任务、公开历史、harness 事实表、学生的提案（尚未执行） | `{decision: accept / guide / demonstrate, facts, need, action, check}`。facts 只能引用事实表中带证据的条目；action 必须是合法格式的单条命令 |
| L：标签 | 该步可用的公开历史和最终执行的动作 | 不超过 64 token 的理由，只用前缀已有信息（复用 M0c 的前缀一致性检查） |

### 1.2 诊断池 U_dev

U_mech 只有 20 个任务，CG 有区分度的案例只有 2 个，因此需要扩大诊断池：
- 从 TRAIN 中另取 60 个任务组，按 6 种任务类型分层，与 K20、U_mech、D_probe、训练池都不重叠，写入 split 文件后冻结。
- θ₀ 对每个任务跑 1 次 greedy 和 4 次 T=0.7 采样，用于预筛。
- 失败案例按预先登记的决策点取前缀：首次见到目标后、首次相关动作被拒绝后、首次进入变换或两物体阶段时、执行完第 10 个动作后（搜索类）。
- 按 A 分支在 4 次采样中的成功数分为三层：0/4（地板）、1–3/4（中间）、4/4（不再算失败案例）。地板案例不删除，单独报告。

## 2. 阶段 1：V1a — teacher 从同一前缀接管

- **案例**：CG 的 7 个前缀（全部保留，按已有 A 分支结果分层），加上 U_dev 中预筛出的前缀，预计 30–40 个。
- **执行**：每个前缀跑 4 次 teacher 接管（teacher 的默认采样），剩余步数与学生相同。如果从前缀接管失败，另从任务起点跑完整的 H=40 作对照。
- **记录**：发现目标的时间与当时剩余步数、拿取、必需变换、失败后如何继续，以及每次调用的 token。
- **输出**：每个前缀的"可行续程"标记，即 teacher 在剩余步数内至少成功一次。teacher 也失败的前缀单独列出，作为接口或可解性的诊断，不进入 V1b 的主比较。
- **通过条件**：多数前缀存在 teacher 可行续程。否则先检查前缀是否已经耗尽完成的可能（与起点运行比较），以及 teacher 接口。

## 3. 阶段 2：V1b — 学生执行，teacher 与 harness 持续指导

### 3.1 G 的单步流程

1. 学生根据公开历史生成 Thought/Action，作为尚未执行的提案。
2. harness 更新事实表；teacher（R 角色）审阅提案。
3. 结果为 accept：直接执行学生的动作。
4. 结果为 guide：在当前 observation 末尾追加 `Guidance:` 段，写明当前事实、待满足的条件或信息需求、一条合法动作，以及执行后要检查什么。学生重新生成一次。
5. 如果重新生成的动作仍然不可执行、重复已被拒绝的动作，或违反事实表中的前提，就由 teacher 示范一步（T 角色），并标记为 teacher 动作。
6. 执行动作，读取真实 observation，回到第 1 步。
7. 每步都调用 R（设计 §2.3.3 的默认做法，不以减少调用为目标）。

### 3.2 对照组

在 V1a 有可行续程的前缀上，各组使用相同的起点、步数上限和评价标准：

| 组 | 做法 |
|---|---|
| U：学生自主 | 不加指导 |
| T：teacher 接管 | 来自 V1a |
| G：持续联合指导 | 按 §3.1 |
| G1：一次性指导 | 与 G 的第一条指导完全相同，之后撤除指导 |

- 学生每组跑 1 次 greedy 和 8 次采样，随机数在各组间共用，与 CG 相同。
- U 和 G1 重新跑，不直接沿用 CG 的旧分支。

### 3.3 指标

**主指标**（每个前缀 8 次采样的平均，再对前缀取平均）：
- 原任务成功；
- 拿到目标；
- 发现目标。"发现时间"的分布里，未发现的单独计数。

**机制指标**（按设计 §3.2.4）：
- 相对 U 改变了行动的比例；
- 是否照建议执行；
- teacher 示范的步数；
- 持有条件是否得到处理（腾手、合法拿取）；
- 被拒绝之后的行动与真实状态是否一致；
- 重复无效动作的次数。

**通过条件**（预注册时写死）：在 V1a 可行的前缀上，G 的成功率比 U 高，并且多数前缀同向；同时 G 中 teacher 示范的步数占比不超过一个预先登记的上限，以免实际上变成接管。具体阈值在预注册中给出。

### 3.4 结果模式与对应的下一步

| 结果模式 | 下一步 |
|---|---|
| T 改善，G 没改善 | 修指导的表达和交还方式（例如把 action 改成必须执行，把示范的门槛放低），然后重测 V1b |
| T 和 G 都改善 | 进入 V2 |
| G 推进了局部进展，但最终没完成 | 定位后续新条件，扩展事实表和审阅规则；同时保留局部监督 |
| T 和 G 都没改善 | 检查前缀留下的完成空间和 teacher 接口 |

## 4. 阶段 3：V2 — 学习并在无提示下检验

- **训练池**：从剩余的合法 TRAIN 任务中预先固定 200 个任务组，按类型分层，与 K20、U_mech、U_dev、D_probe 不重叠。
- **采集**：
  1. θ₀ 在训练池上无提示执行（1 次 greedy 和 1 次采样）；
  2. 对每个失败，从起点和预先登记的决策点运行 G；
  3. 由 E0.4 生成记录。

### 4.1 四个训练组

全部从 θ₀ 出发，使用同一个 SFT 实现、同一个训练任务池和同一个 checkpoint 选择规则：

| 组 | 新监督的来源 | teacher 调用 |
|---|---|---|
| CONTINUE | 只用原 K20 示范继续训练 | 0 |
| OFFLINE | 同一训练池上 teacher 独立执行的成功轨迹。full-TRAIN 收集里已有这些任务的 teacher 轨迹，直接复用 | 0 |
| PREFIX-EXPERT | 学生执行到失败前缀，由 teacher 接管完成（OEC 式），取接管段作为监督 | 接管段 |
| JOINT | G 日志中的局部有效决策和完整成功行为 | 来自 G |

### 4.2 其他设置

- **附加对照**：在 JOINT 的同一批日志上，比较"只用完整成功的监督"与"同时使用经过验证的局部有效决策"。
- **监督量**：报告每组的记录数和监督 token 数。如果差异很大，再用等量子集做归因检查。
- **检验**：在 E0.6 的三种无提示条件下，先看第 1、5、20 次 update 的行为变化（短程诊断），再看按 probe 选出的 checkpoint 在 D_probe 60 上的成功率。最后在 dev140 上与 baseline 做配对比较。
- **通过条件**：JOINT 在无提示的 D_probe 和原困难历史上优于 OFFLINE 和 PREFIX-EXPERT，并且对应的行为指标（持有条件、被拒绝后的更新、搜索切换）在无提示下也有改善。

## 5. 阶段 4：V3 — 条件变化练习（V2 通过后再做）

按设计 §2.4.3，围绕已经验证的学习需求，从现有合法训练实例中检索"条件保持"和"条件变化"的对照，例如：
- 看到 newspaper 时手是空的，还是还拿着无关物体；
- 动作被拒绝前与被拒绝后的历史；
- 不同房间里已经排除的位置不同。

比较 JOINT 内"普通任务补充"与"按条件组织的练习"。先完成 K20，再按同样流程扩展到 K10、K30、K100，复用主网格的 checkpoint 和评测协议。

## 6. 资源与时间估计

### 6.1 teacher 用量

按主网格收集时的实测：teacher 的 ReAct 调用平均约 5,100 input / 63 output token。R 角色（结构化审阅）按 CG 提示生成的实测，约 1,500 input / 1,300 output token（含隐藏推理），带上历史以后估计约 6,000 input / 1,000 output。

| 阶段 | 内容 | 估计调用数 | 估计 token（input / output） |
|---|---|---:|---:|
| V1a | 约 40 个前缀 × 4 次接管，加上必要的起点对照 | ~4,000 | ~20M / 0.3M |
| V1b | 约 30 个可行前缀 × 9 次学生 rollout × 每步一次审阅（G），加上 G1 | ~7,000 | ~42M / 7M |
| V2 采集 | 约 140 个失败任务 × 2 个起点 × G，加上 PREFIX-EXPERT 接管 | ~10,000 | ~60M / 8M |

这已经远超机制试验原来 5M / 0.5M 的上限（目前已用 0.47M / 0.17M）。设计文档写明本阶段不限制 teacher 用量，但仍需要你确认新的上限。我会按阶段设硬上限，所有运行共用一个全局计数器（同一个 key 存在 429 竞争），用尽时干净地停止。

### 6.2 算力

- 学生的服务、rollout 和继续训练都在 rai 上进行（单卡运行 vLLM 约 16 GB，LoRA 继续训练约 29 GB/卡），始终留至少一张卡给其他人。
- K 扩展阶段和 dev140 配对评测放到 hpg。

### 6.3 时间

| 阶段 | 估计用时 |
|---|---|
| E0.1–E0.3 实现与验收 | 约 1 天 |
| V1a | 约半天 |
| V1b | 约 1 天 |
| E0.4–E0.6 与 V2 采集、训练、检验 | 约 2–3 天 |
| V3 | V2 通过以后再定 |

## 7. 需要确认的决定

1. **teacher 上限**：建议 V1a + V1b 合计不超过 70M input / 8M output；V2 采集在 V1b 通过后另行确认。如果想减半，可以把 V1b 每格改为 1 次 greedy + 4 次采样，约 25M / 4M。
2. **诊断池 U_dev**：另取 60 个 TRAIN 任务组，只做诊断、永不训练，是否同意？
3. **G 的审阅频率**：第一版每步审阅（设计文档的默认做法）；"只在事件触发时审阅"作为之后的消融，是否同意？
4. **训练与评测位置**：V2 在 rai 上训练和评测（单 seed），K 扩展时再用 hpg，是否同意？
